# Collaborative boards

Choose **Share board** in the canvas to create a shared board in the owner's Puter account. The application builds and deploys its worker automatically. The owner (and facilitators, for roles below facilitator) can create facilitator, editor, commenter, or viewer invitations, optionally as guest invitations for people outside the organization, copy them, revoke invitations, and change or remove members through **Participants**. Invitations expire after seven days. Existing members can reopen the ordinary board link without an invitation. Boards can also be opened to everyone in the organization or to anyone signed in with the link, subject to organization policy; see [Organizations](organization.md). Puter sign-in is required; workshops can collect anonymous input (see Facilitation). A change to a person's own role while the board is open is told to them once by a notification, and a viewer or commenter sees **View only** or **Comment only** beside **Shared board** over the canvas for as long as it lasts.

## Document and editor

`src/collaboration/document.js` projects a Yjs document into the existing Canvas renderer. Items retain their IDs. Text uses `Y.Text`; style properties use individual map entries; geometry is one register to avoid combining coordinates from competing moves. Concurrent geometry edits resolve deterministically. Layer ranks have an ID tie-break. Deleting a frame or endpoint detaches surviving children/connectors in the projection.

Yjs updates can arrive more than once or out of order. State-vector reconciliation supplies missing edits. Undo tracks this browser's transactions, groups typing, and treats completed moves/resizes as individual actions. Remote activity does not create local undo entries. Shared text is published as it is typed: Escape finishes editing, rather than discarding text others already received. IME replacements are transformed through remote text changes. An object deleted by someone else while this person types in it closes their editor with a notification that names who deleted it, when exactly one other person had it selected in the ten seconds before and the facilitator has not made the board anonymous, and offers to copy the text typed.

Incoming document changes are rebased onto any unfinished local gesture. Previews live outside the durable document, hit testing, thumbnails, and exports. Local selection, viewport, favorites, and interface preferences are not shared.

Each sticky note names who added it: the person a workshop recorded, or else the owner of the Yjs client whose edit first wrote the note's entry. The worker already ties every client to the first account that added content under it and refuses anyone else's content under it (`wb:<room>:client:<id>`), so the `creators` request answers which accounts own the clients a browser asks about, read in one request and remembered while the board is open; nothing is added to the document. The accessible object list says who added each note, and people who turn on **Show sticky note authors** (Preferences or command search, kept on the device) see the name in the note's bottom padding; exports and previews never show it. Notes added under anonymous input, notes face down for this person, and, while anonymous input is on, notes no workshop recorded name no one. Undoing someone's deletion writes the note again under the undoing browser's client, which it then names. Workers from before this request leave notes unnamed.

Mind-map nodes retain ordinary object IDs and text bindings. Their atomic `mindMap` metadata records parent, direction, automatic layout, and branch-line style; sibling order uses the existing numeric `order` field. Branch lines derive from the hierarchy rather than separate persisted connectors. Automatic child positions derive from tree structure and dimensions, avoiding competing coordinate writes for simultaneous additions. Root and manual-map geometry retain normal shared registers. Concurrent reassignment cycles are broken deterministically at the greatest node ID; deleted parents leave surviving nodes as independent roots at their stored fallback positions. Missing relationships and cycles are rejected in imported files. Root movement and branch reassignment preserve automatic layout; manual child movement/resizing disables it. Drag reassignment publishes the hierarchy only on drop. Remote text edits survive the gesture and local undo; changed branch membership, geometry, grouping, locks or removed targets invalidate the gesture. Draft geometry is excluded from local snapshots written while a mind-map drag is active. Local undo keeps remote nodes and text, subject to these deterministic projections. Existing workers require the bundled update for mind-map metadata. The 5,000-node tests establish bounded traversal/layout behavior, not hosted collaboration throughput.

Table matrices project to the same plain arrays used by local boards, JSON, and the renderer. New shared tables hold a bounded `Y.Map` of dimensions and per-cell `Y.Text` values. Independent cell edits and concurrent character edits merge; local undo preserves remote changes. Older array-backed tables acquire per-cell overrides in their existing item map, so simultaneous first edits to different cells survive. Simultaneous first edits to the same legacy cell use the map's deterministic winner; subsequent changes use its shared text. Row/column insertion or deletion replaces the matrix atomically. Competing structural changes select a whole matrix; stable row identities and structural-operation merging are not implemented. Limits remain 20 rows, 12 columns, and 2,000 plain-text characters per cell. Existing workers need the bundled update to accept this representation.

Custom row heights and column widths use independent numeric registers in the matrix map, with the original geometry providing defaults for untouched tracks. Legacy array tables keep these overrides in the item map. Simultaneous first resizes to different tracks merge, and local undo retains other clients' track changes. Snapshots derive total dimensions and connector endpoints from the merged sizes; concurrent sums above the board limit are proportionally bounded. Structural replacement starts a new matrix, preventing stale resizes from being applied to different row/column indices. Undo of a structural replacement restores the matrix known when it was replaced; concurrent edits to the discarded matrix are not merged into that restored copy. Resize gestures remain private previews until release.

Tags use a shared `tags` catalog keyed by stable tag IDs; each catalog value holds the name and color. Independent `tag:<id>` registers on objects merge membership changes, including simultaneous first assignments. Catalog changes and membership participate in local shared Undo. Removing a catalog entry hides any stale references immediately; queued edits filter references to deleted definitions. Concurrent assignments above eight tags project deterministically to the first eight IDs, and the next saved edit removes surplus references. Catalog definitions are atomic registers, so concurrent edits to the same definition use the deterministic winning value. Concurrent creation of separate definitions with the same label keeps distinct IDs; ordinary creation and cross-board paste reuse matching names. The catalog supports 1,000 tags, and this representation requires the bundled worker update.

Direct cell input is a private draft until saved. A changed cell, changed dimensions, lock, or viewer transition blocks stale submission and retains the draft for the current browser session. Other cells can continue to receive shared edits. The properties dialog merges untouched remote cells and rejects competing edits to the same cell or matrix shape. Cell text is not broadcast on each keystroke. The editor keeps one text input and one accessible active-cell node; its 5,000-object navigation test does not establish shared-document capacity for 5,000 full tables.

Each object's optional `objectLink` is one atomic register containing either an HTTP/HTTPS `url` or a relative `objectId`. Link changes participate in local/shared undo and preserve concurrent content edits. Open link forms reject stale submissions and viewer/lock changes. Direct shared-object URLs use the worker/room identity and require normal board membership; copied URLs contain no invitation or query credentials. Personal-object URLs resolve only against this browser's saved boards. Duplicated/copied targets are remapped together; references outside clipboard, template, and partial-export selections become URLs back to the source board. Whole-board copies keep their relative destinations.

Comments use a separate Yjs map with per-thread position and resolution registers and per-message maps. Concurrent replies retain distinct identities; queued saves merge by thread and message ID. Comment changes do not enter object Undo/Redo. Pins project their object's current position, including shared undo; removed anchors detach using the saved fallback. Private comment drafts and visibility stay on the device.

The worker rejects changes to another author's message or immutable author metadata, new messages attributed to another account, and hard removals of existing threads/messages. Editors can resolve/reopen or reposition a discussion; viewers cannot write. Delete comment is a recoverable marker: original text remains in the document, backups, and retained edit records. Creation/import can retain historical authors; when sharing a personal board, this device's local messages acquire the owner's authenticated identity. Limits are 500 threads, 100 messages per thread, 5,000 messages total, and 4,000 characters per message. Commits the worker checks at the same time can together cross a limit; because discussions cannot be removed, every client then shows the oldest discussions and messages that fit, and the worker refuses changes that add to a count already over its limit, so the board stays saveable. Commenters can add and edit their own messages but no content: the worker refuses any update from them that writes to objects, the title, tags, or the timer, even with unchanged values, which would still win over editors' concurrent changes, and their saves write only discussions and workshop registers. The same holds for anyone rewriting another person's message with its own words, and, while a facilitator locks the board, for participants rewriting objects they may not change, the title, tags, or the timer. Likewise only owners and facilitators may write facilitator workshop registers, and participants may write only their own ballots, answers, reactions, contribution and attendance records. When a commit adds messages, the worker notifies board members mentioned with @username, organization members another member mentions on a board shared with the whole organization before they first open it (unless they were removed from it), and earlier participants in the thread, kept by the board's worker and listed in the app's Notifications whichever worker hosts the board (see [Organizations](organization.md)); in the app, a discussion with a message from someone else newer than this device last opened it shows an unread dot on its pin and counts on the Comments button (what was read is kept on the device for the fifty boards opened or read there most recently, and comments already on a board the first time it is opened there count as read), and a message mentioning the person while the board is open shows a notification that opens the discussion. Reactions on messages are facilitation registers (see [Facilitation](#facilitation)). Existing workers need the bundled update for comment support.

## Tasks and planning

Task metadata is one atomic `task` register per object (sticky notes, shapes, and text): `{ assignee: { id, name } | null, start, due, status, priority?, jira? }`, with ISO `YYYY-MM-DD` dates, status `todo`, `in-progress`, `blocked`, or `done`, priority `low`, `medium`, or `high`, and an optional Jira link `{ key, url, status? }`. `validateBoard` checks every field strictly (known keys only, real calendar dates, start on or before due, HTTPS Jira URLs), so the worker rejects malformed task data from any client. Because the register is atomic, simultaneous edits to different tasks merge, while simultaneous edits to the same task keep one complete winning version rather than mixing fields. Task edits use ordinary local and shared Undo, one step per change.

A connector between two task objects can carry `dependency: "blocks"` (its start blocks its end) or `"depends-on"` (its start depends on its end), stored as its own field. Dependencies are derived at read time: a task is blocked while any predecessor is not done, and connectors whose endpoints are no longer tasks are ignored rather than rejected, so concurrent deletions stay valid.

Board-level planning settings live in the board metadata map as one `planning` register. Today it holds `statusSync`, the Kanban option that updates a task's status when it moves into a frame titled after a status ("To do", "In progress", "Blocked", "Done", or the French equivalents). The update happens on the client that moved the task, inside the same edit and Undo step. Commenters cannot change planning settings; the worker includes them in the content signature it compares for commenter commits.

When a commit newly assigns a task to someone, the worker's `recordActivity` compares the before and after snapshots and, for assignees who are current members of the board, stores an `assignment` notification (`org.notify`) and a `board.content.task_assigned` audit event. Reassigning to the same person, assigning a non-member, or free-text assignees on personal boards produce no notification. The acting member is audited but not notified about their own assignment. Notifications follow the organization's existing delivery rules (in-app list, optional email, and webhooks).

Jira synchronization runs through the organization worker, which holds the Jira site, account, project, and API token (`org.jira.create` and `org.jira.status`). The browser offers **Send to Jira** and **Refresh Jira status** only when the organization allows the Jira integration and the board lives on the organization's worker; otherwise it explains why. Created issues are stored on each object as `task.jira`; refreshing updates `task.jira.status` only. Existing workers need the bundled update to validate task and dependency fields and to send assignment notifications.

Embeds store their canonical `url` (an existing register), `provider`, and title text; the iframe address is derived from the URL on each client, and `validate()` rejects any embed whose URL does not normalize to its provider. Tables imported from Google Sheets keep a `sourceUrl` register holding the Google Sheets link and A1 range; refreshing replaces the matrix like any structural table change. Live iframes, their open state, and import progress stay local. Imported images and attachments are ordinary objects and travel as file assets. Existing workers need the bundled update to accept these properties.

## Workshop timer

The optional board timer is one atomic Yjs register in a separate `timer` map, outside drawing Undo/Redo. Its run ID, state, duration, remaining paused time, and running deadline travel through the existing authenticated edit/outbox path. Editors may start, pause, resume, extend, and reset; the worker rejects viewer writes. Simultaneous commands converge to one complete state under Yjs conflict resolution; concurrent time extensions are not added together. Offline commands retain the same queued-edit behavior as drawing changes.

Join/sync/commit responses include worker time. The client estimates transit time from half the request round trip (ignoring responses taking ten seconds or longer), then advances that clock with `performance.now()`. This reduces device-clock skew without extra network requests; latency asymmetry and resynchronization can still change the displayed second. Older workers without clock metadata fall back to the device clock and need updating to accept timer state. A personal running timer's deadline is converted to the shared clock when sharing completes.

Countdowns are derived from the deadline, including after tab suspension/reload. Local 250 ms display ticks never persist edits, scan objects, or repaint the canvas. Completion is derived without a worker job or a write per tick. Visual alerts and optional synthesized chimes occur once for an observed running deadline; expired timers opened later do not replay an alert. Chimes require browser audio activation and remain a local preference. There are no OS notifications for closed tabs. Timers support up to 24 hours; exports, imports, board duplication, and reusable content do not carry an active workshop into a new board. Reusable content keeps the agenda steps of the frames it holds; inserting it adds them to the board's agenda for an owner or facilitator, and anyone else inserts the frames alone.

## Facilitation

Reactions, dot votes, polls, private mode, anonymous input, participant locks, staged frames, the agenda, attendance, and completed results live in one `workshop` Yjs map, outside drawing Undo/Redo like the timer. Every value is an atomic JSON register; nothing is nested Yjs content. `SharedDocument.validate()` accepts the map and rejects nested types, and `validateBoard()` checks each register through `src/facilitation/model.js`.

| Key                   | Contents                                                                             | Written by                        |
| --------------------- | ------------------------------------------------------------------------------------ | --------------------------------- |
| `settings`            | Lock (`open`, `contribute`, `frozen`), private round, anonymous input, staged frames | Owner or facilitator              |
| `session`             | Workshop recording window used by the summary                                        | Owner or facilitator              |
| `agenda`, `run`       | Step durations and instructions keyed by frame; the running step                     | Owner or facilitator              |
| `vote`, `poll`        | Current session configuration, state, and reveal flag                                | Owner or facilitator              |
| `h:<id>`              | Completed vote or poll results (up to 50)                                            | Owner or facilitator              |
| `v:[vote, account]`   | One participant's ballot                                                             | That participant                  |
| `a:[poll, account]`   | One participant's poll answer                                                        | That participant                  |
| `r:[account, target]` | One participant's reactions to an object or comment message                          | That participant                  |
| `c:[object]`          | Who added an object while a workshop was running, and its private round              | The object's creator              |
| `p:[account]`         | Attendance during the current session                                                | That participant or a facilitator |

Participant-owned keys include the account ID, so concurrent votes, answers, and reactions from different people are separate registers and always merge. Queued local changes are rebased per register. Limits are 20,000 registers, 10,000 reaction registers, 2,000 ballots, 2,000 poll answers, 5,000 contribution records, 512 attendance records, 50 completed results, 20 votes per person, 5,000 votable objects, 12 poll options, and 60 agenda steps.

The worker applies `validateWorkshopChanges()` to every commit, after `validateCommentChanges()`. Only owners and facilitators may change `settings`, `session`, `agenda`, `run`, `vote`, `poll`, or history. Everyone else may only add, change, or remove registers whose key and `by` field match their authenticated account, and any recorded name must match their account name. Ballots must belong to the current open vote (with five seconds of grace after a deadline), stay within its votes per person, refer only to its objects, and repeat an object only when several votes are allowed; anonymous sessions cannot record names. Poll answers follow the same rules. Reactions must target an existing object or message. While anonymous input is on, new or changed reactions and contribution records cannot record names. Facilitators may clear ballots from earlier sessions but never change a ballot of the current one. Whoever may delete content may clear reactions and contribution records left on deleted objects. A contribution record can only be created, by its creator, in the same commit as its new object. `contentSignature` still protects titles, objects, tags, and the timer from commenters; workshop registers are excluded from it because they are checked per author instead. Viewers cannot commit at all.

While `settings.lock` is `contribute`, the worker only accepts participant commits that add sticky notes with their own contribution record, or change or delete objects recorded as their own; titles, tags, and the timer are fixed. While `frozen`, participants cannot change any content; votes, answers, reactions, and comments continue. Owners and facilitators are exempt. Moving your own note can also change a connector attached to someone else's object, which the lock then rejects. Objects created before the lock have no contribution record and count as someone else's. The client mirrors these rules before saving, restores the last saved content, and explains why; the worker's rejection is authoritative.

### Private mode, anonymous input, and staged frames

Private mode, anonymous input, and staged frames hide content in the app. They are not encryption. The shared document, local recovery copies, backups, and the worker's retained edit log contain every note's text and every contributor's account ID, and each client receives the whole document. A participant with developer tools could read hidden notes or link entries to accounts. We chose this deliberately:

- Notes remain ordinary synchronized objects. A private note is never lost when its author closes the tab, goes offline, or leaves before the reveal, and the reveal reaches everyone at once as one register change.
- Keeping private text out of the document until the reveal would need each author's browser to publish its notes when the facilitator reveals them. Absent authors would silently delay or lose contributions, and editing text outside the shared text binding would bypass collaborative editing and undo.
- Encrypting notes to the facilitator would still let the facilitator read everything, and would break search, exports, and editing until the reveal.

Within the app, a sticky note created while private mode is on records the private round in its contribution record. Until the facilitator reveals contributions, every other participant, including facilitators, sees a face-down placeholder: the canvas, the accessible object list, board search, image and document exports, Whiteboard file exports, and typing previews show "Private note" instead of its text, and editing is blocked. The worker also rejects changes to someone else's private note until the reveal. Staged frames cover the frame title and omit their contents from the canvas, hit testing, and exports for participants until the facilitator reveals each frame. The console states this limitation next to the private mode control.

Anonymous input stores new contribution records and reactions without names, and while it is on the worker refuses new or changed ones that carry a name; those named before it began stay as they are. A device that saved a reaction or a new note before it heard of the switch, such as one offline, has that edit refused and makes it again without its name, so the note and the reaction are kept. Anonymous input also reports contributions only in aggregate in the summary, and replaces names on live cursors and editing indicators with "Participant". Turning anonymous input on or off redraws everyone's cursor and outlines rather than renaming them in place, and each anonymous round gives each person a new color, so a cursor cannot be followed from its name into the round or out of it. After the round, someone selecting or editing a note written anonymously is still shown on that note as "Participant", in a color of its own. Anonymous votes and polls never record names, and their results never list voters. Account IDs remain in participant-owned keys so the worker can enforce one ballot per person. Comments keep their author, as the worker requires. The worker's edit log, `lastEditor`, and the organization audit log still identify the authenticated account behind each change, so anonymity applies among participants, not toward board owners or administrators.

### Agenda, attention, and results

The agenda follows the board's frame order (the same order as presentations and **Frames and navigation**), so templates whose frames are ordered steps work without extra setup. A frame titled with its timebox, such as the playbooks' "1 · Set the stage (10 min)", runs for that long unless the agenda sets another duration (0 for no timer). `agenda` stores optional durations, instructions, and excluded frames by frame ID, and is kept when a board is duplicated, imported, or exported. Starting or advancing a step writes `run`, focuses the facilitator's view on the frame, asks everyone to follow through the existing attention request, and starts the shared timer with the step's duration. If the step's frame is staged and not yet revealed, or hidden from participants, the same save reveals it: a staged frame moves up to the frames already shown, so frames left out of the agenda stay covered and **Reveal next frame** continues with the rest in order. A step frame lying inside a larger frame that is still hidden or staged stays covered with it, since showing that frame would show its other contents too, and the facilitator is told so. Following requires a live peer link; participants without one still see the step banner and can open the agenda, where **Go to current step** moves their own view to the step's frame, as it does for anyone who joins late or looks elsewhere.

A timed vote closes for everyone at its deadline; the first facilitator client that observes it records the results. Ending a vote or closing a poll writes a result record to history, which is exportable as CSV (with spreadsheet formula protection) or JSON. Anonymous records contain counts only.

Attendance is recorded while a workshop session is active. Each participant who can write records their own presence, and facilitators also record everyone in the live roster, including viewers; entries refresh at most every five minutes. The summary derives contributions from contribution records, comments, reactions, ballots, and poll answers in the session window, and bounds activity over time to twelve intervals.

### Live reactions and raised hands

Live reactions and raised hands are not part of the `workshop` map. Choosing one of the eight reaction kinds from the smiley control in canvas navigation sends a signed `reaction` peer packet carrying only the kind and the time; every client, the sender's included, floats the emoji up the board for about two and a half seconds, or fades it in place when the device asks for reduced motion, and then removes it. The sender's name shows under it unless anonymous input is on, in which case no one sees who sent it. Nothing reaches the Yjs document, the outbox, exports, or Undo, and the control is shown only on shared boards; without a live peer link its choices are disabled.

Everyone on the board may send live reactions, viewers included, as an audience does, and so may participants of a locked or frozen board, as frozen boards already allow reactions. A client sends at most three in any second. Receivers drop a reaction whose kind is not one of the eight, whose time is more than fifteen seconds from their clock, or that comes from someone who has left, take at most five a second from each sender, and drop the rest. A relay that drops one does not pass it on, so excess reactions do not cross the room. At most thirty float on a screen at once; others arriving meanwhile are dropped, though a person's own reaction always shows, in place of the oldest. Reactions are relayed to every member like edits, not filtered by view as presence is. Clients without live reactions ignore the packet kind, and relays running them pass it on unchanged.

**Raise hand**, in the same popover, is a toggle (`aria-pressed`) that anyone on the board may use, viewers included, and the control shows a small raised hand while it is up. A raised hand travels with the person's live view, as an optional `hand` field holding the time it went up, so everyone keeps it while that view is live, people who arrive later learn of it from the next renewal, and it goes when the person leaves (their final `view-left`, or the twelve-second view lease). A relay passes a view at once when the hand in it changes, rather than spacing it with the camera samples. Receivers refuse a view whose `hand` is not a whole number at or before the view's own time. Clients without raised hands read the view as before and ignore the field.

Owners and facilitators see raised hands in the order they went up, one per person however many tabs they have, in **Participants** and in the People tab, which also marks the person's row, and the participants button shows them a count. Each raise and lowering is said through the board's polite live region, with changes within a second gathered ("Hand raised: Bob", or "3 hands raised."). They can lower one person's hand or all of them: a signed `hand` packet names one session or `all` with the time of the request, and every receiver checks that the sender is an owner or facilitator, that the request is within fifteen seconds of its clock and newer than that sender's last, then takes down the hands raised before it. The person whose hand it was lowers it, so their next view says so, and is told "A facilitator lowered your hand."; a view renewed before they heard still carries the hand, which receivers keep down until it is raised again after the request. Anyone lowers their own hand from the popover or from the list, without a live link if need be. Other participants see the same list, by name unless anonymous input is on, in which case they see only how many hands are up and no row says whose; facilitators keep the names, as they call on people. No lock prevents raising a hand.

### Audit, compatibility, and copies

For each accepted commit, the worker writes organization audit events for facilitation changes in the content category: `vote.started`, `vote.ended`, `vote.revealed`, `poll.started`, `poll.closed`, `poll.revealed`, `workshop.private_mode`, `workshop.locked`, `workshop.anonymous`, `workshop.staged`, `workshop.hidden`, `workshop.protected`, `workshop.agenda`, and `workshop.session.started` or `workshop.session.ended`.

Boards without a `workshop` map load and save unchanged; an empty map adds nothing to the document. Workers that predate this map reject documents containing it until the owner opens a shared board and the bundled worker update is deployed. Imported and duplicated boards keep the agenda, completed results, and reactions, and drop live settings, sessions, votes, polls, ballots, attendance, and contribution records. Whiteboard file exports do the same for the whole board and omit workshop state for partial exports. In a copy or export made by someone other than an owner or facilitator, each reaction left anonymously keeps its count under an ID of its own instead of the account that left it, so the file's comments cannot put a name to it. When a personal board is shared, this device's ballots, answers, reactions, and contribution records move to the owner's account.

## Puter worker and storage

The browser sends a restricted Puter access token that can only read a small identity file containing a public signing key. It never sends its app session credential to an invited worker, and public health checks carry no credentials. Requests are signed over the destination server, identity-file path, and request-body digest. `worker/auth.js` validates the token through a strong `user.puter.fs.stat()`, reusing the answer for 30 seconds per token and identity file; Puter's `/whoami` endpoint rejects scoped access tokens. The stat result must identify an unshared file owned by the caller (`is_shared: false`; Puter returns `null` for another user's file). Only after that validation does the worker trust the token's user UUID, use the file owner's username, and check the request signature. Possessing the restricted token does not let another board owner read personal boards, change cloud files or KV, or impersonate that collaborator on an updated worker.

Credentials expire after 24 hours and renew before expiry. The private signing key and token stay in app KV with sharing disabled, scoped to the issuing app session. Reloads and board switches reuse credentials to respect Puter's minting quota. Worker proof caches are bounded and short-lived. Token expiry is checked on every request; revocation takes effect within the 30 seconds Puter's validation is reused, within the 90 seconds a peer ticket stays valid. The request signature and board access are checked on every request. Already-open clients using app credentials remain compatible with updated workers; restricted tokens cannot bypass signature verification by omitting their proof. Previously deployed workers update when their owner next opens a shared board. Until that update finishes, the new client still limits the credential's cloud permissions, but an old worker cannot enforce the destination binding.

`BoardService` accesses the owner's resources through `me.puter`. ACLs and signing keys are outside the editable document. Only the worker owner can create boards on that worker. All reads, writes, assets, and roster operations check membership. Viewer commits are refused by the worker, independently of disabled UI controls.

The app bundles the worker with `npm run build:worker`; both `npm run dev` and `npm run build` include that step. The generated `public/worker/whiteboard-worker.js` ships in `dist/worker/`. Per-account deployment metadata lives in `whiteboard-collaboration-worker-v1` in app KV. Sharing a personal board deploys or updates the app-scoped worker using `puter.workers.create()` and `puter.fs.write()`. Opening an existing shared board as its owner also checks for updates in the background, once per app session. Organization requests check before calling the API, so the owner can update a broken worker by opening the organization without first opening a shared board. Only a worker matching this account's saved deployment is eligible; invitation URLs cannot trigger creation or updates of other workers. A failed update leaves the API available and can be retried on the next check.

The worker admits at most two KV listings at once. Waiting requests poll admission metadata with timers belonging to their own request: waiting only on a promise resolved by another request makes Cloudflare cancel the waiter as hung. Admission tickets and active listings expire after twenty seconds, so a cancelled or stalled request cannot permanently block the queue. A storage timeout returns a retryable JSON 503 through the normal route rather than a runtime error without CORS headers.

The outbox stores local document updates in IndexedDB before uploading them. Immediate peer traffic carries only transient previews. Updates are merged into short persistence batches; acknowledgements identify the exact batch checksum. Retries do not overwrite another contributor's record. The save indicator distinguishes pending changes, live synchronization, periodic fallback, and connection/access failures. An acknowledgement lost after a successful write is safe to retry. Edits the worker deterministically rejects, such as simultaneous additions that together cross a board limit, are not retried: the client saves the accepted prefix of the batch, discards the rejected edit, reloads the shared state, makes what each later queued edit changed again on top of it (changes to anything the rejected edit added go with it), and shows a notice. Commits checked at the same time can still together take a board past its object, tag, or workshop register limits, or a note or table cell past its length limit when two people type into it; the worker then refuses only changes that add to a count or lengthen a text already over its limit, and clients open and synchronize such a board, so everyone else's edits keep saving. Switching boards waits for local outbox writes; reopening resumes uploads and pending edits.

Images and attachments are content-addressed files. The client uploads them before committing references, verifies downloaded checksums, and hydrates them into the existing embedded-data representation for local recovery and exports. Media bytes never enter KV or peer packets.

Every edit batch stays in the log (**this implementation deliberately retains the edit log**), which is what makes version history and point-in-time restoration possible. Loading does not replay it: the worker keeps an immutable checkpoint of the whole document, written once at least 256 new records have accumulated or a day has passed, and records a pointer to it with the time it was taken. An instance first takes up a checkpoint another instance wrote since, and a busy board is checkpointed at most every five minutes unless 4,096 records build up, so a workshop with a hundred people editing a 5,000-object board keeps about a dozen 2 MB copies an hour rather than one per instance every few seconds' worth of edits. A load reads that checkpoint plus only the records written from two minutes before it. Record keys start with their time, so the log is read newest first, 200 records a request, up to the first earlier record (a refresh's first request asks for 20 plus one and a half times as many as the previous refresh found, at most 200): a load or refresh reads no older records, and takes one request unless there are more new records than that, however long ago its starting point. An earlier version is read forward from its checkpoint by ISO time prefix (minute, hour, or day, whichever keeps listings few), up to the first later record. Applying a record twice is harmless in Yjs, so the overlap safely covers records that became visible late, and a stale pointer written by another instance is still a superset of what it saw. Boards from before this change keep their older `op:` records, which are read only until their first checkpoint covers them.

Version history (`history.list`) groups the log into versions, newest first, 300 a page; `before` asks for the versions older than the last one shown. Each version is named by the time of its last edit (`at`), which `history.state` takes to rebuild the board as it stood then. After the oldest edit, the list ends with the board as it was created (`original: true`, at the board's creation time, named after the person who created it, which a transfer of ownership keeps), so content a board started with, as from an import, a template or a copy, can still be restored when its first session removed it. `history.state` at that time, or any earlier one, returns the starting content without any edit, even one stamped in the same millisecond; the list shows such edits just after it.

A board's worker shares Puter's KV request quotas among everyone on its boards: about 40 requests a second for each kind of request, but only 240 listings a minute on paid plans (120 on free ones), at most five (three) at once. Listings read in full therefore fetch 1,000 rows a request, and each worker instance also caches: immutable snapshot, checkpoint, and large-update files (up to 48 MB); a recent document state per board (reused as is for 1.5 seconds, then checked against the board's event signal, and extended by each commit it accepts; see below), with the four most recently used boards also kept loaded as documents, so commits are checked and synchronizations answered without decoding the board; board metadata, memberships, organization user records and the organization's policy, while their access stamps are unchanged (see below); each board's list of members for five seconds, taking in the member records the instance writes, for the member list participants' editors ask for as they join and open comments, and for comment notifications, which check each recipient's access (counts, indexes and assignment notifications list members afresh), so people joining a workshop together list them about half as often (150 people joining a 20-editor room within a minute on the paid quota: one to three failed joins instead of 32, saves in 6 to 7.5 seconds at the 95th percentile instead of 9); and the list of people present on each board (see below). Directory, search index, and content audit records are written at most once a minute per board and instance, with counts added up in between; an instance whose last stored search text matches the board's reads the stored text back and writes it only if another instance changed it. A commit may claim at most 32 Yjs clients the board has not seen (a browser commits from one, or a few after reloads), since each costs a write and a record kept for good; one naming more is refused. In steady state a commit costs about 2.6 KV requests, a synchronization about 1.5, and a check-in about 1.2 even with 300 people present, whatever the history length, nearly all of them gets and sets: about one commit in eight, one synchronization in thirty and one check-in in fifty lists anything. `tests/worker-capacity.test.js` checks this, and also simulates a minute of a 300-person room on three instances, with 40 editors saving eight edits a second between them and two people told of each save synchronizing for it: the worker makes about 200 listings (250 with five quiet boards beside the room), at most two at once per instance, 26 gets (32 with the quiet boards) and 24 sets a second. Under Puter's paid listing quota no request fails, and saves take 1.6 seconds at the 95th percentile; under the free one, at half what the room asks for, 9 seconds (3 to 15 across orders of the same requests, before access stamps as after), still without failures or lost edits. Clients upload an edit made after a quiet spell at once, and space later uploads by how many people uploaded in the last fifteen seconds, as peers announce them: 0.4 seconds for a few, 1.25 for ten, 12.5 for a hundred and at most 15 from 120 on, keeping a room near eight commits a second however many people edit. Moves, drawings and typing reach others live over peer links meanwhile, so the wait delays only saving, not what people see. With a hundred people editing a 150-person room, each saving every 3 seconds as the earlier 3-second ceiling allowed, the worker would make 240 listings a minute (all of the paid quota) and 57 sets a second, retry 3,273 requests and take 10.5 seconds per save at the 95th percentile; paced this way it makes 143 listings and 20 sets a second, with no retries and saves in 63 ms. A device without peer links, whose edits nobody sees until they are saved, waits at most 3 seconds and counts a quarter of a large room. Moves, drawings and typing show live meanwhile, and a finished one stays shown until its edit arrives. Its author's presence says it is settling, repeated each second, until their outbox is empty (at least long enough for the edit to be sent, at most twenty seconds), so the hold follows a save that waits its turn, is retried, or meets a slow worker. Others hold it for six seconds, or until four seconds after its author last said so, never more than twenty: presence from someone working out of view reaches a large room's members once a second, and a hold ends soon after its author goes quiet, as when they disconnect. Older clients say so for a few seconds after the gesture, so their holds last about six seconds as before. The presence ending a cancelled gesture says it is not settling, so nothing of it is held. Each finished object is held on its own: a drawing or connector finished just before its author starts the next stays shown while the next is drawn, and gives way only once the board has it, not when an earlier one's edit arrives. Moves of existing objects still give way to any edit from their author, since some, such as mind-map moves, save no new position. Clients check in every 40 to 45 seconds in rooms over thirty people, while peers keep carrying live edits.

Who may open a board is checked on every request, from the board's metadata, the caller's membership and organization user record, and the organization's policy. Each board has an access stamp (`wb:<room>:access`), and the organization one (`org:access`), rewritten with a new value after any of these change. An instance reads each stamp at most once a second, for all requests, and keeps each record while the stamp keeps the value it was read under, for at most 30 seconds. An access check reads whatever it cannot use, and any stamp due, in one request, as Puter counts a get of several keys as one. Changes made through an instance apply to it at once. Removing someone, changing their role, archiving or deleting a board, deactivating an account or changing the policy applies on other instances within about a second: their next read of the stamp, at most a second later, plus the time a write takes to show in reads. A record read just as a new value was first seen may not show the change yet, so it is kept two seconds, as all were before stamps. A stale stamp read, or a stamp write that fails, delays a change by 30 seconds at most, and never makes an instance use a record that was not stored. Someone joining leaves the board's stamp as it is, as an instance that read their membership as absent reads it again after two seconds, so a wave of joins does not have every instance read everyone's records again (with someone joining every three seconds, the simulated minute makes 30 gets a second, not 48); the record created for a guest as they first join leaves the organization's stamp, as instances without it already treat them as a guest. Workers from before stamps do not write them: while an owner's update rolls out, a change made through an instance still running the previous version applies on updated ones within 30 seconds, and changes made through updated ones apply on the previous version's within the two seconds (ten for account status) it keeps records.

Every save writes the board's event signal after its record, with a value never written before; workers from before this change do too. An instance checks its copy of a board by reading the signal. While the signal keeps the value the instance first read, every record was saved before then, so once the copy's last listing began 1.5 seconds after that, when listings surely show those records, the copy holds them all and the log is not listed. Otherwise the instance lists the log, from 15 seconds before its previous listing, and it lists it at least once a minute anyway, in case a save's signal was lost. Polls use the copy as it is while a check runs; a caller told of a save waits for a check begun after it asked, which everyone asking meanwhile shares, and which lists the log whatever the signal shows, so a stale read of the signal never hides a record someone was told of; such checks list the log at most once a second per instance, the callers told of saves meanwhile waiting for the next. A commit building on edits the copy lacks waits for such a listing too, so commits refused together share one rather than each listing the log. No clock is compared with another instance's. Polls of a board no one is changing therefore read one value instead of listing the log. Check-ins likewise reuse an instance's list of the people present for two seconds. After that the list is kept while the board's roster stamp, written whenever someone joins or leaves, keeps the value read before a listing begun 1.5 seconds later, as for the signal, until a ticket it holds could lapse: people still present renew theirs before then, through whichever instance. Joins and departures through another instance show within a few seconds in rooms of any size, and saves do not have the list read again. Each instance runs at most two listings at once, its own and the organization's, and queues the rest. Puter's SDK sends a listing Puter refuses for its quota again for about twelve seconds before failing, so once a listing is refused, or one has run for two seconds, the instance treats listings as scarce (for ten seconds after a refusal): synchronizations and check-ins are answered from the copies it holds, naming back any record the caller was told of that a copy lacks, so the client asks again; nobody waits more than three seconds for a listing; and a commit building on edits its copy lacks is refused with status 409, which clients send again 1.5 seconds later. A load with no copy to fall back on still waits its turn.

## Live transport

Live navigation carries world-space camera rectangles and the followed session through signed ephemeral peer packets. A camera change after a pause is sent at once, which lets relays pass on presence near the new view without waiting; further movement coalesces into 100 ms samples, or 200 ms in rooms over thirty unless someone follows that view, since everyone verifies every view. A three-second idle pulse keeps views live. Packets older than fifteen seconds are rejected, and a twelve-second lease (checked every two seconds) removes lost views independently of the roster. Normal departure attempts a final signed `view-left`; unexpected exits use lease expiry. Cameras and follow requests never enter the Yjs document, outbox, exports, or Undo. Periodic worker synchronization does not carry them; older clients and unavailable peer links show **Waiting for live view**.

Editors can ask an individual or everyone to follow; viewers can only follow. A request reaches only the people present when it is made, so someone following no one, not presenting, and followed by no one is offered, in the follow banner, to follow a live presenter, or else whoever at least two others follow; dismissing the offer hides it until someone else leads. Each receiver independently verifies the sender's role and request target. Sequence numbers reject old camera samples and repeated requests. Busy editors receive a pending invitation instead of losing a draft or dialog. Manual navigation cancels follow, and cyclic follow chains are rejected. Different screen sizes fit the same world rectangle within the normal zoom bounds; forwarded follow chains retain the original rectangle rather than repeatedly enlarging it. Presentation frames use that same path. Follower counts, search, and cursor visibility are local UI state; hidden cursors retain selection outlines. Participant lists keep at most fifty live rows.

`puter.peer.serve()` advertises each session. `connect()` is followed by the actual connection-open event, with connection/handshake deadlines and late-result cleanup. Server `connection` events use `event.conn`; `reconnect` renews the advertised invite. Closed or disconnected links are dialled again every five seconds, and all data channels, connections, timers, and event subscriptions are closed when leaving. When others are present but no peer link has connected for ten seconds, longer than dialling a dropped one again takes, the participants button adds **No live view**: their cursors and changes in progress cannot arrive, though their saved edits still do through the worker. It goes once a link connects.

Connection lifecycle guards also run after asynchronous identity verification, so a disconnect cannot restore a dead link and permanently occupy its retry slot. Already-received signed packets may finish verification after their transport closes; closing the local network prevents further delivery.

The worker signs short-lived membership tickets binding identity, role, room, and an ephemeral public key. Peers prove possession through a connection-specific challenge, signed together with the certificate fingerprints of that connection's encrypted transport, so a participant cannot pass another peer's answer off as their own. Forwarded packets retain the origin signature; another participant cannot choose someone else's contributor identity. Most of a small packet, such as a cursor's, is its sender's ticket and the two signatures, so each link carries a ticket only until the other end says it keeps it (it keeps up to 1,024 per link); later packets name it instead and are checked exactly as the full packet would be, and a link that has lost a named ticket says so and is sent it again. Clients from before this never say so and always receive full packets. With 150 people moving cursors, a relay sends about half the bytes it did (2.4 rather than 4.7 MB a second). Every recipient checks room membership, ticket expiry, and role. In large rooms each packet arrives from both of a group's relays, often at once; a copy that arrives while another is being checked waits for that check instead of repeating it, and is checked itself only if the other proved forged. Permission changes stop worker access within about a second (immediately on the instance that made them; see [Puter worker and storage](#puter-worker-and-storage)); existing peer tickets can remain valid until roster refresh or, at most, their 90-second expiry.

Small rooms (up to eight sessions) use a full mesh. Larger rooms form groups of up to 32, each with two relay candidates. Ordinary members connect to their group's two relays; relays connect across groups. The primary forwards local traffic across groups, and the secondary takes over when its primary link closes or has carried nothing for two seconds. A quiet primary is asked after every second with the connection challenge peers already answer, so when a primary's device crashes or loses its network without leaving, its group reaches other groups again within about two seconds instead of the 25 to 33 that ending the link takes (measured in a 64-session room; a relay that leaves closes its links, and the secondary takes over at once). A member whose relays have all gone, as when both of its group's relays leave together, checks in at once for the roster naming their successors rather than at its next check-in, up to 45 seconds away, since members of large rooms do not follow board events; and after each roster change a peer dials missing links again a second later, as the other end may have refused the first for not yet having that roster. Measured with both relays of a 32-member group leaving, its members were cut off for 1 second plus a check-in instead of until their next check-ins. Remote-group packets are distributed locally rather than flooded back across all groups. Current clients ask the worker for a lasting group at check-in: a session joins the fullest group with room and keeps it, with its join time, while it checks in, and each group's two longest-present sessions relay. Someone joining or leaving then changes only their own links, unless they relayed (measured at 300 sessions: 2 links per join, against about 380 of 750 when groups were runs of sorted session IDs). A roster containing any session without a lasting group, such as an older client's, falls back to groups of sorted session IDs, so every client computes the same links. At 512 sessions, the steady-state bound is 61 connections for a relay and two for an ordinary member, with a hard local connection budget of 64.

Cursors, editing indicators, selection outlines, and geometry/drawing previews are throttled to 25 Hz in rooms of up to eight people, 10 Hz up to thirty, and 5 Hz beyond, since every participant receives and verifies everyone's, and use an unordered WebRTC data channel with zero retransmits. In rooms over eight, a relay passes a member of its group someone's presence at that rate only while its cursor, previews, selected or edited objects, or the connectors attached to objects it moves or edits and those connectors' other ends (as the relay's board places them, up to 100 per packet) fall within the member's last shared view widened by half its size on each side, or just left it; otherwise at most once a second per sender, with the latest sent once the sender pauses. When a member's shared view moves, its relays at once send it the latest presence (if under two seconds old) of each sender now near that view that it was not sent, so cursors where someone pans or jumps to are current rather than up to a second behind. The start or end of settling, a preview's end, a change of the object being edited, and presence for members whose view is unknown always pass; other packets and relay-to-relay traffic are unaffected. Congested channels drop previews instead of accumulating stale movement. Cursor rendering interpolates between samples and respects reduced-motion preferences. Sequence numbers reject old previews, including previews arriving after a final edit. Activity expires independently of the participant roster. Reliable peer packets carry small document updates only after persistence, with a worker-signed receipt binding the update checksum, room, and authenticated contributor. Recipients verify this receipt before applying an update. A rejected edit therefore cannot become permanent through the peer path. Typing previews remain transient until their corresponding document changes are accepted. Oversized updates recover through the worker.

Each person's name shows once, on the object they are editing or else the first of theirs in view; several people on one object share one tag, the editor's first and in their colour ("Alice · Editing, Bob", then a count past three), rather than covering each other's. Cursors and name tags are drawn for sighted people only, so screen readers get presence another way. In the **Board objects** list, an object someone else is typing in is described as **Being edited by** with their names, or **Participant** where a facilitator has made input anonymous. Joins and departures, as the participants button shows them after each check-in, are said through the board's polite live region: changes within three seconds are gathered, so one person reads as "Alice joined" and several as "3 people joined"; in rooms over thirty people they are not said at all.

## Events and recovery

Browser subscriptions use `puter.events.onLocal()` and handle `{ event }`. The owner subscribes within the app namespace. Other participants receive worker-minted KV share handles after the owner's `manage:kv-share` consent. Handles expose only the non-sensitive signal region; they never expose board data, ACLs, invitations or signing keys.

In larger peer rooms, only relays maintain direct event subscriptions. Peers distribute edit and commit traffic; a relay whose synchronization brings an edit no peer announced, such as one made through the API or by someone without peer links, asks everyone to synchronize, at most every two seconds; every participant still reconciles periodically and after connection/visibility changes. Subscriptions are established before initial synchronization and retried when they lapse. Events, including gap markers, only trigger reads of persisted state. Correctness does not depend on receiving every event or on `includeValue`. A synchronization prompted by a board event or a peer's `committed` notice says so and names the records it was told of: the signal's value, read with `includeValue`, carries the ids of the edits saved, and a `committed` notice carries its own. A worker instance whose copy of the board lacks any of them, or that is told of an unnamed save (a relay's nudge, or an event delivered without its value), checks its copy again with a check begun after the request arrived, shared with everyone asking meanwhile, instead of answering from that copy; a copy holding every named record answers at once, so the first participant to ask reads a save for everyone told of it. Records still missing afterwards, as when a listing lags a write, are named back, and the client asks again a second later, up to three times. A named record whose edit then arrives over a peer link, often just after its notice, is no longer asked for, and periodic polls name nothing, so the instance answers them from a recent copy. Without this, a save made through another instance, as a guest elsewhere often reaches, could stay unseen until the next periodic synchronization, 20 to 45 seconds later. The decision never compares the copy's own time with a save's time: a time stamped by another instance or by Puter's event service says nothing sure about this instance's clock, and a listing begun before a record became visible must not pass for one made after, which an earlier version got wrong whenever someone drew quickly. The save's time still travels (`after`) with a notice, for workers from before record ids were named.

Current [Puter limits](https://docs.puter.com/rate-limits-and-quotas/#events) include 128 free / 512 paid matching subscriptions per KV event per region, based on the key owner's plan; separate live-handle quotas; 600 broadcast deliveries per minute per subscription; 250 ms event coalescing; and a 16 KB inline-value ceiling, with values omitted above 128 matching subscriptions. KV events cannot be replayed with `events.fetch()`. The app therefore works with periodic synchronization when events or delegated handles are unavailable. Puter-managed TURN is used through the peer API; peers require signed-in accounts.

The status beside the board name shows a disruption apart from the saved states: offline, retrying, unreachable or refused access in the warning colour and a lost board, a failed recovery, an incompatible worker or a save that failed on this device in the error colour, each with an icon and in heavier type (both colours meet 4.5:1 on either theme). A connection or board disruption that lasts 2.5 seconds is also told once by a notification, unless another notification is already showing, and its end once more (**Back online · changes synced**); a blip shorter than that only changes the status, and repeated failures during the same disruption say nothing more.

## Verification and operating limits

Automated tests exercise concurrent edits and text, coherent transforms, deletion conflicts, local undo, duplicate delivery, out-of-order delivery, paginated storage, authorization, invitation expiry/revocation, signed identity, file assets, missed events, offline outbox recovery, lost acknowledgements, topology/failover, and independently initialized built editors.

The 512-session figure is a topology ceiling, **not a demonstrated production capacity**. KV/worker throughput, list quotas, retained-log replay, presence heartbeats, relay bandwidth, browser load, and TURN costs may impose lower practical limits. Large-room load testing and authenticated multi-account testing against the hosted Puter service remain necessary before advertising a production room-size guarantee. Connection topology tests do not substitute for that testing.

Local and personal boards retain their original file-backed backup workflow. Sharing converts that board's active persistence to the worker; its personal cloud file keeps the shared-room reference. JSON imports and board duplication produce independent personal copies. Clearing browser storage removes unsent edits and cached assets, so pending changes should be synchronized or exported first.

Image sources now travel with crop and container geometry as one Yjs value. Snapshots can still read the previous separate source field, and commits retain that field as a compatibility mirror for older workers. Current clients use the atomic value when concurrent replacements and transforms conflict. Shared asset bytes remain file-backed; only their references enter the document. An incoming replacement cancels an unfinished transform against the old source, while unrelated label/style edits remain independent.
